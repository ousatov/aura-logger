## Where AI helped
- Read the contract, KDoc and SDK API, then wrote all four classes and the screen in one pass; the build was green on the first run.
- Invalidation on `EventTracker.changes`: the Pager factory keeps a reference to the current `EventsPagingSource` and a collector in `viewModelScope` invalidates it.
- Seen reporting without duplicates: one concurrent set in the ViewModel holds ids already reported and ids loaded with `seen = true`.
- Displayed rows: `snapshotFlow` over `LazyListState.layoutInfo.visibleItemsInfo`, mapped via `LazyPagingItems.peek` (so footer rows are skipped and no load is triggered), debounced 500 ms.

## Where AI was wrong or had to iterate
- Left an unused `Button` import in the first draft of the screen; removed before building.
- Loop risk: `markSeen` emits `changes`, which reloads the list and shows the same rows again. This is harmless only because reported ids are skipped. It was caught by reasoning, not by a test.

## AI version vs final version
```kotlin
// AI version
items(count = items.itemCount, key = items.itemKey { it.id }) { ... }
// visible ids taken from LazyListItemInfo.key as String
```
```kotlin
// Final version
.filter { it.index < items.itemCount }
.mapNotNull { items.peek(it.index)?.takeUnless(EventItem::seen)?.id }
```
Footer rows also have String keys, so reading ids from item keys would report them as events.
